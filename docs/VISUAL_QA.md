# Visual QA: component gallery and computed-style baseline

## What it is

`/__gallery` is a development-only page. It draws 42 samples (buttons, fields, chips, states, cards, icons, type) with the
**real stylesheets**, in the scope the real page gives them, plus a theme switch. The route does not exist when
`APP_ENV=production` (it answers 404), and it is served with the same strict CSP as the site (one external script, no inline script).

`frontend/gallery.html` is generated by `python build_frontend.py` from `frontend/gallery.template.html`; it is not edited by hand.

## Capture and compare

1. `python run.py`, open `http://127.0.0.1:8000/__gallery`.
2. The key is `theme@bucket`, where bucket is `phone` (width ≤ 480), `tablet` (≤ 1000) or `desktop`. Resize the window to each bucket and press *Light* / *Dark*.
3. In the console:
   - `mbVisualCompare(baseline)` returns the list of differences against a saved file (`docs/visual-baseline.json`, section `hashes`). It names the sample that changed.
   - `mbVisualSnapshot()` returns the full computed values (20 properties per sample and the colour tokens). Use it before and after a change to see **which property** moved.
   - `mbVisualFingerprint()` returns the short hashes that go into the baseline file.
4. After an intended visual change, capture the six keys again and replace `docs/visual-baseline.json`. Review the diff: every changed hash should match something you meant to change.

`tests/test_gallery.py` checks that the baseline covers every sample in all six keys, that the two themes really differ, that saved, saving, unsaved and failed are told apart, that the page is generated, and that the route is 200 locally and 404 in production.

## What it catches, and what it does not

Catches: changes to colour, border (top edge, plus the left edge, which the save states use; right and bottom are not read), radius, type family/size/weight/line height, padding, size, shadow, cursor and opacity, and changes to the colour tokens.

Does not catch: layout flow between elements, anything painted (gradients, background images, SVG drawing), fonts that fail to load (the family is read, not what was drawn), motion, or the real page's behaviour. It is a tripwire for the shared look, not a screenshot comparison. The baseline was captured in one Chromium; another engine can differ in `lineHeight` or `fontFamily` serialization.

A bug found while building it: the first fingerprint ignored the left border, so *saved* and *saving* hashed the same. Properties were added until the four save states were distinct, and a test pins that.

## Inconsistencies the gallery showed, and what became of each

- **Control radius:** unified at 5px on Tools, Library, Chat, Contact and Self-check (measured). The gallery's "global" samples sit outside any page and keep the old 6px and 14px.
- **Unstyled text field outside a page scope:** fixed. A zero-specificity baseline (`:where(...)` in `paper.css`) gives fields a border, radius, 44px minimum height and the 13px type; every field that other sheets style keeps its own look (measured on the real pages: heights 44-49px, no overflow).
- **No type scale:** fixed. Tokens `--fs-xs` to `--fs-2xl` (12, 13, 15, 18, 24, 32px); bare h1-h4 use them at zero specificity.
- **Chip family type:** fixed (13px/500 for the three chips; simplify from 401px up). Baseline recaptured.
- **`btn-sm` equals the secondary button:** left as is on purpose; it is an alias in the markup, not a separate design.
- **Field height (46px) against buttons (44px):** left on purpose. Real fields measure 44-49px depending on the page; a field a little taller than a button is not a defect, and every one is at least 44px.
- The baseline was recaptured after the type-scale change and verified: a hash of every sample the change should not touch matched the previous baseline for all six keys, and the changed samples (h1, h2, h3, the global fields and the welcome card heading) were replaced.
